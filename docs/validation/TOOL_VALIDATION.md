# Tool validation statement (appendix)

Guide section 22.7, in the spirit of NIST's Computer Forensics Tool Testing (CFTT) programme: what
each function of dfirbench is expected to do, how it was tested against known inputs, the results
and versions, and the known limitations. Generated parts come from
`scripts/tool-validation.py` (machine-readable copy: `tool-validation.json`); `--check` runs in
the test suite, so a parser, fixture, golden file or rule change that is not re-validated fails CI.

## Method

* **Known inputs.** Every parser has at least one fixture with a reviewed golden output
  (`backend/tests/fixtures/golden/*.json`). The EVTX fixtures are public samples (see
  `test_parsers_golden.py` for their source and licence); all other fixtures are synthetic and
  generated by `backend/tests/fixtures/deep/make_fixtures.py` (no real personal data).
* **Expected behaviour.** Each parser accounts for every record (`records_read == emitted + skipped
  + errors`), emits UTC timestamps with the original string kept, never raises on a single bad
  record, and is bounded (line, record, size, decompression, time and output caps). Hostile-input
  and fuzz tests (`test_parsers_hostile.py`, `test_parsers_deep_hostile.py`) cover the failure
  side; this appendix records the known-input side.
* **Recorded results.** For each case: the fixture's SHA-256, parser version, record accounting,
  the SHA-256 of the normalised output (exactly what is stored in `events`, including the
  deterministic event ids) and whether it equals the golden file.
* **Detection.** Every built-in rule has a positive scenario that must alert and a near-miss
  negative scenario that must not.
* **Integrity.** Each integrity requirement of guide 22.3 is mapped to the automated test or live
  smoke that proves it.
* **Sandboxed execution (Phase 10).** In the deployed stack every parser runs in the parser
  sandbox container. `test_sandbox_protocol.py` proves for every case below that the sandbox
  protocol is lossless (the stored rows are byte-identical to in-process parsing), and
  `phase10-smoke.py` runs a job through the real sandbox.

## Limitations

* **External engines.** `tsk_fs` (Sleuth Kit `fls`/`mmls`), `volatility` (Volatility 3) and
  `zeek` are validated here as wrappers against recorded engine output (fake binaries in
  `tests/fixtures/deep/fake_tools`): argument building, output parsing, caps, timeouts and the
  clean environment. The engines themselves are validated by their upstream projects; the live
  Phase 6 smoke runs the real `fls`/`mmls` in the worker image on a FAT12 image and checks a clean
  failure of Volatility without symbol packs. Zeek is not installed in the worker image.
* **Synthetic fixtures.** Registry hives, Prefetch, Amcache, LNK, browser databases, PE, PCAP,
  wtmp, shell histories and journal exports are synthetic (written by the fixture generator to the
  published formats). They prove the parsers' behaviour on the documented structures; layouts not
  covered by a fixture (for example Windows 8.x ShimCache, dirty hives with transaction logs) are
  listed in `docs/parsers.md` and `docs/BACKLOG.md`.
* **Cross-tool comparison** (guide 22.2 item 2) against Plaso/Hayabusa/EZ Tools was not run: those
  tools are not part of the Standard-profile images (BACKLOG, post-v1).
* **Detection coverage** is measured on the rule fixtures, not on public labelled attack datasets;
  the ATT&CK coverage table is `docs/detection-coverage.md`.
* **Time zones.** Sources without an offset (syslog) depend on the analyst-supplied time zone and
  year; the run manifest records both, and the Kolkata golden case shows the conversion.
* **Versions.** Results are for the versions listed above; any upgrade of a pinned package or
  engine requires re-running this script and reviewing the diff.
